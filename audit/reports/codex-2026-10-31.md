### M-01: Oversized X1 burns require governance intervention to unlock

- **Opis:** The Ethereum ISM uses a hard token bucket with maximum capacity `RATE_CAP`. A message whose amount exceeds that capacity always fails, even after unlimited waiting. The X1 synthetic configuration does not establish a matching outbound maximum. Once burned, the message amount cannot be reduced or split. The repository explicitly reproduces this behavior in `test_M2_oversizedUnlockRecoverable`.
- **Scenariusz ataku:**
  1. A user acquires more VMPXe than the Ethereum bucket capacity.
  2. The user submits one X1 transfer exceeding that capacity.
  3. X1 burns the tokens and dispatches the message.
  4. Ethereum rejects processing with `RateLimitExceeded`.
  5. Retries continue failing until governance increases capacity or changes the verification configuration.
- **Wpływ:** Funds are unavailable for an unbounded period without administrator cooperation. Recovery through the production timelock takes at least its configured delay. This is a per-message liveness failure; it does not establish that unrelated messages are blocked.
- **Rekomendacja:** Enforce a compatible maximum before burning on X1, including coordination when governance lowers capacity. Alternatively, implement an authenticated delayed settlement mechanism that can eventually settle oversized messages without increasing the security limit. A frontend warning alone cannot enforce this restriction.
- **PoC:** Existing `evm/test/ReviewFixes.t.sol:44–58` burns `RATE_CAP * 2`, demonstrates failure, then raises capacity and retries successfully. Not executed during this review.

### M-02: X1 authority verification can report success without checking expected authorities

- **Opis:** The E2E authority check supplies `--mint` and `--program`, but no expected upgrade or metadata authority. The checker emits `WARN` when those expected values are absent, and only failures produce a nonzero exit status. Consequently, E2E can print an authority-check PASS while a deployer EOA still controls program upgrades. The checker also does not inspect the token configuration owner responsible for ISM and router changes.
- **Scenariusz ataku:**
  1. An operator deploys the testnet route and omits an intended authority transfer.
  2. The E2E authority check completes successfully despite warning about the unchecked authority.
  3. The operator interprets the PASS as confirmation of the authority model.
  4. A compromised retained upgrade key replaces the synthetic program, allowing unbacked minting or malicious burn-message generation.
- **Wpływ:** The verification workflow cannot establish the documented ownership model. If promoted into production acceptance, retained deployer authority can compromise bridge backing without the expected Squads approval. The scripts are explicitly testnet scripts; retained testnet authority itself is not presented here as an unauthorized production deployment.
- **Rekomendacja:** Require expected authorities for acceptance checks and fail closed when they are absent or cannot be resolved. Verify the token configuration owner, enrolled router, ISM, and relevant core/ISM upgrade authorities as well. Pass those expectations from the E2E script.
- **PoC:** `svm/compat/check-x1.mjs:103–116` selects `WARN` for missing expectations; lines `125–126` return success when there are no failures.

### L-01: Fixed price windows do not enforce the advertised rolling 24-hour bound

- **Opis:** `MAX_DAILY_PRICE_CHANGE_BPS` is described as a bound per rolling 24-hour window at line 56. The implementation resets an anchor when the current fixed window expires. Price changes immediately before and after that boundary belong to separate windows.
- **Scenariusz ataku:**
  1. A compromised price bot starts from anchor price `P`.
  2. Near the end of the window, it makes permitted hourly updates to `1.2P`, `1.44P`, then `1.5P`.
  3. At the window boundary, the anchor resets to `1.5P`.
  4. The bot makes another permitted 20% update to `1.8P`.
  5. The price has increased 80% within several hours despite the configured 50% “rolling” daily bound.
- **Wpływ:** A compromised bot can alter the reference price faster than advertised, changing ETH fees. The independent ETH fee cap still applies; this does not move collateral.
- **Rekomendacja:** Implement a genuine rolling constraint using time-indexed observations, or explicitly document fixed-window semantics and choose limits accounting for boundary effects.
- **PoC:** The sequence above satisfies both the 20% step limit and each fixed window’s 50% anchor limit. `evm/test/ReviewFixes.t.sol:123–139` tests within-window rejection but not this boundary case.

### L-02: Deployment accepts zero initial reference price, disabling bot recovery

- **Opis:** The constructor assigns `_initialPriceWeiPerToken` without requiring it to be positive. With an old price of zero, every positive bot update fails the relative-change check: `diff * 10_000 > old * MAX_PRICE_CHANGE_BPS`.
- **Scenariusz ataku:**
  1. Deployment mistakenly sets `INITIAL_PRICE_WEI=0`.
  2. The deployment succeeds.
  3. The price bot attempts to publish a positive price.
  4. Every update reverts.
  5. Governance must announce and execute a delayed price reset.
- **Wpływ:** The normal price-update mechanism is unavailable. Fresh quotes charge the minimum fee; after staleness, fallback pricing applies. Recovery requires governance and the hook’s three-day reset delay.
- **Rekomendacja:** Reject zero initial prices in the constructor and deployment validation.
- **PoC:** Substitute zero for the initial price, wait the update interval, and call `updatePrice(1)` as `priceUpdater`; the relative-change check rejects it.

### L-03: Validator validation permits weaker security than the specified 7-of-10 model

- **Opis:** Deployment accepts any nonempty validator set with at least a 60% threshold. It therefore accepts 1-of-1 and 6-of-10, although the stated X1 attestor model is 7-of-10. The threshold is also narrowed to `uint8` without an explicit upper-bound check.
- **Scenariusz ataku:**
  1. An operator supplies ten valid addresses and threshold six.
  2. Deployment passes its security sanity checks.
  3. An attacker compromises six validators.
  4. Those validators authorize fabricated X1 messages, despite the documented expectation that seven keys are required.
- **Wpływ:** An accepted deployment can provide weaker attestation security than the specified model. Forged unlocks remain subject to the configured rate limiter and pause mechanism.
- **Rekomendacja:** Enforce the intended production validator count and threshold, or require an explicit reviewed security profile. Validate the threshold’s representability before casting.
- **PoC:** For ten validators and threshold six, `6 * 10 >= 10 * 6` passes line 117.

### I-01: Direct donations invalidate the stated exact collateral equality

- **Opis:** Disabled LP deposits and minting do not prevent direct ERC-20 transfers or inherited `donate()`. These increase lockbox collateral without creating synthetic supply or an in-flight message. Inherited `donate()` is also payable and does not refund attached ETH.
- **Scenariusz ataku:**
  1. Anyone transfers one token base unit directly to the lockbox, or calls `donate()`.
  2. Lockbox balance increases.
  3. Synthetic supply and in-flight liabilities remain unchanged.
  4. The exact equality specified in `audit/SCOPE.md` fails.
- **Wpływ:** Exact-equality invariant checks can produce false alarms. Donated tokens create no withdrawal claim. ETH accidentally attached to `donate()` has no identified recovery path in the current implementation. This does not create undercollateralization or let the donor withdraw existing collateral.
- **Rekomendacja:** Express solvency as collateral being at least outstanding liabilities and track surplus separately. Document unsupported donations and reject attached ETH where possible; direct ERC-20 transfers cannot be prevented.
- **PoC:** Existing `evm/test/ReviewFixes.t.sol:150–164` demonstrates that donations create no redeemable shares.

### I-02: Rate bucket permits almost twice its capacity within a 24-hour interval

- **Opis:** The configured limiter starts full and refills continuously over one day. It limits burst size and sustained throughput, rather than total withdrawals in every rolling day.
- **Scenariusz ataku:**
  1. An attacker controlling the required attestors submits forged unlocks consuming capacity `C`.
  2. The attacker continues submitting withdrawals as capacity refills.
  3. Before 24 hours elapse, nearly another `C` can be consumed.
- **Wpływ:** A capacity described operationally as a “daily limit” can allow almost `2C` of losses in the first day of an incident. This requires valid messages or compromised attestation; it is not a signature bypass.
- **Rekomendacja:** Document the bound as burst capacity `C` plus refill `C/day`. If the intended maximum loss is a strict rolling-day amount, implement that policy or size the bucket conservatively.
- **PoC:** Available withdrawals over elapsed time `t` can approach `C + C × t / 86,400`.

## Sprawdzone i w porządku

- **Unlock authentication:** Under honest attestors and the configured ISM, the Ethereum path requires multisig verification, unpaused state, and rate capacity. Router handling additionally checks the enrolled remote sender. No unprivileged unlock-without-burn path was identified.
- **Mint authentication:** The intended X1 multisig configuration authenticates Ethereum messages. The EVM lock and dispatch are atomic. Actual deployed X1 program behavior and authority state were not independently verified.
- **Replay:** Ethereum Mailbox delivery tracking prevents a successful message from being processed twice. Failed processing rolls back state, allowing retry after unpause or restored capacity. X1 replay behavior is an upstream dependency, not proven by the EVM stand-in.
- **Fees:** The router pulls exactly the gross amount, transfers the rounded token fee to treasury, and dispatches the net amount. Both remain multiples of `1e9`. The token fee cap is 500 basis points. Inherited fee-recipient configuration cannot add charges, and a nonzero token fee hook causes transfers to revert.
- **Fee bypass/griefing:** No alternative public transfer entry point bypassing the router override was identified. Splitting tiny transfers can eliminate the rounded token fee, as explicitly tested, but each dispatch still incurs the configured ETH minimum.
- **Refunds:** Generated metadata specifies `msg.sender` as refund recipient. The aggregation hook refunds excess ETH to that address. A contract sender rejecting ETH can make an overpaid transfer revert; atomic rollback prevents collateral loss. No refund theft path was identified.
- **Inherited collateral movement:** LP `deposit()` and `mint()` are disabled. Rebalancing requires an allowed bridge, and `addBridge()` is disabled. Adding a rebalancer alone cannot establish a drain path in a fresh deployment. Inherited withdrawal functions cannot redeem nonexistent LP shares.
- **Proxy/initialization:** Implementation initialization is disabled; proxy initialization is supplied atomically to its constructor. ProxyAdmin and router ownership transfer to the timelock. Namespaced bridge-fee storage avoids adding ordinary inherited storage slots.
- **Timelock:** Production Ethereum deployment enforces at least 48 hours. Temporary timelock administration is renounced. No completed-deployment bypass was identified. Fee parameter announcements and price resets additionally enforce their own delay and expiry.
- **Hook ordering:** The configured sender hook includes pause, Merkle insertion, then fee collection. The Mailbox required hook executes first. Failed later hooks revert the entire transaction, including lock and insertion.
- **Decimals:** The configured 18-to-9 conversion and outbound dust restriction preserve representable values. The full immutable token cap fits within a 9-decimal `u64` supply.

Role-compromise assessment:

| Role | Consequence |
|---|---|
| X1 attestor quorum | Can authorize unlocks without real burns, bounded by the current Ethereum limiter and pause state. |
| Ethereum attestor quorum | Can authorize unbacked X1 mints; those tokens can subsequently be genuinely burned to withdraw collateral. |
| Admin Safe | After timelock delay, can upgrade the router or replace verification/configuration and thereby compromise collateral. Existing caps are not guarantees against upgrades. |
| Guardian / registered pauser | Can halt processing; guardian can restart and cancel timelock operations. No direct collateral-transfer authority identified. |
| Price bot | Can manipulate fee pricing within implemented bounds or force stale fallback by withholding updates. No collateral authority. |
| X1 Squads owner / upgrade authority | Can change trusted verification/router configuration or program behavior. Compromise can ultimately threaten Ethereum backing. |
| Relayer | Can censor/delay delivery and lose its hot-wallet funds; cannot independently forge authenticated messages. |
| Deployer | Has temporary wiring authority during deployment. Completed Ethereum handover removes the identified owner/admin powers. X1 authority handover needs explicit verification. |

- **X1 rollback/finality:** Finalized commitment does not protect against an exceptional rollback of finalized history. A burn can disappear after its checkpoint has authorized an Ethereum unlock. This is an acknowledged trust assumption, not a newly discovered implementation defect. The rate limiter bounds throughput, and an operational pause only helps if activated before additional settlement.
- **Secrets:** Example agent configurations contain placeholders and recommend KMS. Runtime agent startup uses environment variables rather than private-key command-line arguments. However, `testnet/import-agent-keys.sh:15` deliberately passes the private key and password through process arguments; a local process observer can capture them. This exposure is already explicitly disclosed at line 5 and remains relevant to the testnet threat model.
